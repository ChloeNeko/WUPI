## The mandate

Build native tool calling for the local Gemma 4 (12B) model so the Wupi
assistant can edit files for the user — combined with a hidden system-log
codex that gives Wupi inherent knowledge of the running system. The API
narrator model does NOT do tool calling (creative/narration only); local
Gemma carries triple duty on local-only setups (tool caller + narrator +
agent tracker).

The original proposal (generated by Gemini) claimed `llama_cpp_2` exposes
`OpenAIChatTemplateParams`, `tools_json`, automatic GBNF generation, and a
`use_jinja` flag. **Verified against the pinned source: none of these exist
in `llama-cpp-2 0.1.151`.** The grammar samplers that DO exist are gated
behind `feature = "common"` (disabled in WUPI's Cargo.toml). The proposal's
CODEX-in-system-prompt claim was also backwards — it would have broken the
delta-prefill invariant. The reframed requirements:

1. Local Gemma = tool caller (edit files for the user)
2. API model = narration/creative only, no tools — local stays the silent
   agent AND handles tool execution when API is active
3. Hidden system-log codex — Wupi reads system logs as inherent knowledge;
   user-invisible, user-uncodable-by-construction
4. Gemma triple-duty on local-only: tool caller + narrator + tracker

## What was built

### Phase 1 — `src-tauri/src/tools.rs` (new, ~1160 lines)

The foundation. Pure-Rust parser + executor + registry + allowlist.

**Parser** (`parse_tool_calls(raw) -> Vec<ToolCall>`): extracts
`<|tool_call>call:name{args}<tool_call|>` markers from
`ParsedOutput.raw` (the documented Gemma 4 protocol token at
`chat_format.rs:145`). Malformed JSON args are carried (NOT dropped) as
`{"raw": "..."}` so the 3-pass repair loop can fold them back into the
next prompt — same fail-proof contract philosophy as `schema_engine.rs`.
`MAX_TOOL_ITERATIONS = 3` per turn (mirrors `MAX_DELTA_PASSES`).

**Allowlist** (`is_writable(path) -> bool`): default-deny predicate with
a hardcoded, non-overridable deny-list pinning load-bearing engine files:
`wupi.exe`, `*.dll`, `bin/`, `models/*.gguf`, `memory/memory.sqlite*`,
`data/wupi.sim`, `data/api_config.json`, `data/theme.json`, `.git/`,
`target/`, `node_modules/`, `assets/`, `paw.png`. Allow-list permits
user-data trees only: `data/docs/`, `data/user.xml`, `apps/fable/`.
`sandbox_path()` rejects absolute + parent-traversal (`..`) before
evaluation. Read-only tools bypass the deny-list.

**Executor** (10 tools, each ~30-60 lines, all wrapping existing pure-fn
I/O):

| Tool | Wraps | Source |
|---|---|---|
| `file_read` | `std::fs::read_to_string` | new, allowlist-gated |
| `file_write` | `std::fs::write` (atomic: temp+rename) | new, allowlist-gated |
| `file_delete` | `std::fs::remove_file` | new, allowlist-gated |
| `file_list` | `std::fs::read_dir` | new, allowlist-gated |
| `create_sim_card` | builds XML, writes `apps/fable/cards/<stem>.sim` | wraps `sim_card.rs` types |
| `delete_sim_card` | `std::fs::remove_file` on cards dir | new |
| `edit_user_profile` | `user_profile::save` | `user_profile.rs:140` |
| `codex_create` | `codex::save_file` | `codex.rs:297` |
| `codex_delete` | `codex::delete_file` | `codex.rs:318` |
| `codex_list` | `codex::list_files` | `codex.rs:244` |

**25 unit tests** cover parsing (single/multiple/malformed/empty-arg),
sandbox (relative/absolute/traversal/dot-stripping), allowlist (every deny
rule + every allow rule + default-deny), and tool round-trips
(file_write→read, create_sim_card→parse, edit_user_profile→load,
codex_create→list→delete).

### Phase 2 — Agent loop in `chat_send` (`lib.rs`, +200 lines)

The integration. Plumbs tools through the whole stack:

- `GenerationClient::stream` trait (`llm.rs`) gains a `tools:
  Vec<ToolSpec>` parameter. All three impls (EchoBackend, HttpBackend,
  LlamaCppBackend) updated. The four call sites in lib.rs updated (chat_send
  local path, two API-fallback paths, fable_send API path).
- `EngineRequest` (`engine.rs:80`) gains a `tools` field. The hardcoded
  `let tools: Vec<ToolSpec> = Vec::new();` at `engine.rs:500` is replaced
  with the request's tools, threaded through `ChatEngine::generate`.
- `run_local_or_echo` (`lib.rs:2817`) threads tools to the backend.

**New `run_agent_loop` helper** (`lib.rs`, the load-bearing piece): wraps
`run_local_or_echo`. Each iteration decodes → parses `<|tool_call>`
markers → executes via `tools::registry()` → inserts
`<|tool_response>` turns → re-decodes. Up to `MAX_TOOL_ITERATIONS = 3`
rounds. If the cap is hit, a final no-tools decode produces prose so the
user gets a reply (not a dangling tool-call echo).

**chat_send dispatch** (rewritten):
- **Local mode:** the agent loop IS the reply path.
- **API mode:** the agent loop runs FIRST as a tool-routing pre-pass on
  the always-resident local 12B. If tools fire → keep local reply, skip
  API. If no tools → discard local prose, hand to API for narration.
  `tools_fired: bool` returned alongside the result gates the API skip.
- The `done` event gains a `tool_call: bool` flag.

**Tool-turn rendering** (`chat_format.rs`): when a tool fires, the agent
loop inserts an assistant turn (with the raw `<|tool_call>` marker —
cache-coherent via the existing `raw_output` verbatim path, Bug #3
preserved) + a user turn carrying a `{"__tool_response__":true,...}`
content envelope. New `render_tool_response_marker()` helper detects the
envelope and emits `<|tool_response>response:name{...}<tool_response|>`
(the documented Gemma 4 protocol token). Deterministic from content →
cache-coherent.

**6 new chat_format tests** pin: tool-call turns render verbatim from
raw_output, tool-response markers render as protocol tokens (and the raw
envelope does NOT leak as literal text), ordinary messages aren't
mistaken for tool responses, tool declarations render in the system turn,
and the helper is deterministic.

### Phase 3 — `fable_send` narrator exclusion guard (`lib.rs`, +58 lines)

The narrator path NEVER gets tools — locked by design. Enforced
structurally (fable_send dispatches to FableEngine, not the chat backend;
`build_narrator_prompt` takes no tools parameter) and now documented +
test-pinned:

- Comment block at the top of `fable_send` explains the structural
  exclusion + the requirement for any future refactor that routes through
  the chat backend (must pass `Vec::new()`).
- `fable_send_never_includes_tools` test: asserts the narrator prompt
  builder emits no `<|tool>declaration:`, `<|tool_call>`, or
  `<|tool_response>` markers.
- `tool_registry_populated_but_narrator_excluded`: double-guard that the
  chat tool registry IS populated (so the agent loop works) while the
  narrator prompt contains none of those tool names.

### Phase 4 — `src-tauri/src/system_codex.rs` (new, ~390 lines)

The hidden system-log codex. Periodic snapshots of WUPI's runtime state
written to the reserved `WUPI_SYSTEM_CARD_ID = "__wupi_system__"`
partition. Wupi retrieves it via the **already-live** `search_wupi_visible`
read path (`memory.rs:696`) — she "knows every nook and cranny" of the
running system without any new IPC.

**Privacy guarantee (by construction):**
- `__wupi_system__` is a Rust constant, never accepted as an IPC argument.
- The user-facing codex UI (`codex_list`/`save`/`delete`) is pinned to
  `CODEX_CARD_ID = "__codex__"` and physically cannot touch the system
  partition.
- `search_wupi_visible` is called server-side inside `chat_send`; results
  fold into the model's `<retrieved_memory>` block, never exposed verbatim.

**Snapshot content** (split under the 1300-char codex chunk budget so
bge-small's 512-token limit isn't hit):
- `system_model_source`: Local vs API + active profile name/model + active
  persona card id.
- `system_fable_state` (only when a game is active): scenario card name.
- `system_conversation`: in-memory session message count + whether a
  schema delta is in flight.
- `system_world_state`: the Wupi-assistant world schema
  (`to_json_pretty()`), only when non-empty.

**Reconcile** (idempotent, hash-gated): each entry body is hashed
(`DefaultHasher`, matching `codex.rs`); unchanged hashes = zero writes
(steady state is free). Changed hashes = delete + re-insert. Orphans
deleted. Mirrors `codex::seed_codex`'s reconcile shape.

**Wiring:**
- `snapshot_system_state(state) -> SystemSnapshot` captures AppState
  fields under brief mutex locks (no lock crosses an await; tokio mutexes
  use `try_lock` with graceful degradation to 0/empty).
- Periodic task spawned in `setup()`: initial snapshot at boot + every 60s
  via `tokio::time::interval`. Detached, lives for process lifetime.
- Post-chat snapshot: `snapshot_system_state` runs at the end of every
  `chat_send` so Wupi's next retrieval has fresh state.

`codex.rs::build_metadata_json` promoted to `pub(crate)` so system_codex
reuses the exact metadata format (the `kind=codex` discriminator is
mandatory for the codex render frame + the lower dense floor).

**9 unit tests** cover snapshot rendering (model source / fable state /
empty-schema omission / chunk budget), hash determinism, and metadata
field extraction.

## Architecture decisions (locked by your answers + verified against source)

| Decision | Rationale |
|---|---|
| **Prompt + 3-pass repair, NOT GBNF** | `llama-cpp-2 0.1.151` gates grammar samplers behind `feature = "common"` (disabled). Enabling it forces a full CUDA recompile (Chloe-owned per `critical_build-safety-no-target-touching.md`). Worse, GBNF defeats JSON *malformedness*, not *hallucination* (`schema_validator.rs:7-14`): a model emitting `{path: "/wupi.exe"}` under GBNF would emit it just as confidently every pass. The Rust allowlist here is the structural defense GBNF cannot provide. |
| **Generic FS tools + allowlist** | "Free reign" was the goal; the option's own caveat ("requires a sandbox/allowlist to be safe") is honored with the deny-list. Default-deny: anything not on the allow-list is rejected. |
| **Local-first for `chat_send` only** | Local model is always resident (§8 v0.6.3). `fable_send` (narrator) excluded by design — narrator = creative, no tools, ever. |
| **Tool turns as `Assistant` + `User` messages** | Avoids a `session::Role` rewrite (which would touch serialization + the archiver's `checked_sub(2)` indexing + persisted save files). The content marker `{"__tool_response__":true,...}` lets the formatter recognize + render tool turns cache-coherently. |

to separate my hunks from pre-existing uncommitted in-flight work (the
2026-07-27 stress-test changes: `api_role_label`/`local_role_label` helpers,
`fable_send` streaming callback rework, test additions). That command
discards ALL uncommitted changes to a file — it reverted both my Phase 2
work AND the in-flight work in lib.rs.

I recovered my Phase 2 changes from my edit history and re-applied them
(committed correctly in `58d3a81`). **The in-flight lib.rs changes were
lost** — they were never committed, and `git reflog` only tracks
commits/resets, not working-tree state. The Phase 2 commit message
documents this. The other in-flight files survived intact (`bracket_parser.rs`,
`fable_command.rs`, `prompts.rs`, `narrator_prompt.rs`, `data/gm.sim`,
`data/wupi.sim`) — only lib.rs was affected.

If the role-label / fable_send streaming changes need to come back, they
can be reconstructed from the diff content captured in the session log
(the agent's recon subagent quoted them at length). They are NOT critical
to tool calling — my code uses `Vec::new()` for tools on the API stream
path, which works without the role-label helpers.

**Lesson:** `git checkout <file>` is destructive on uncommitted work. For
isolating hunks, the safe path is `git stash --keep-index` (or
`git stash -p`) which preserves the working tree. I should have used that.
